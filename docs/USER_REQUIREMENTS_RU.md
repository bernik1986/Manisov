# CrewDeck CRM — требования для пользователя

Документ описывает, как система должна вести себя с точки зрения конечного пользователя.

---

## 1. Общие требования

- Пользователь входит в систему по логину/паролю и попадает на Dashboard.
- Система должна сохранять авторизацию, корректно завершать сессию и переводить на `/login` при невалидной авторизации.
- Навигация по разделам должна быть стабильной: Dashboard, Seamens Data, Templates, Notifications, Users/Logs (для admin).

---

## 2. Требования по ролям

- `admin` видит и использует все разделы, включая Users и Logs.
- `recruiter` работает с данными кандидатов и шаблонами в рамках разрешений API.
- `viewer` работает в режиме просмотра, без административных функций.

---

## 3. Кандидаты и карточка кандидата

- Пользователь может:
  - создать пустую карточку кандидата;
  - загрузить анкету (DOC/DOCX/XLS/XLSX/PDF);
  - загрузить CV (PDF);
  - открыть карточку из списка;
  - использовать поиск/фильтры/пагинацию.
- В карточке кандидата пользователь может переключаться между разделами и сохранять изменения.
- Для удаления сущностей в карточке должны быть подтверждения:
  - Sea service;
  - Family contacts;
  - K. Flag documents;
  - Candidate (удаление всей карточки).
- При отмене подтверждения удаление не выполняется.

---

## 4. Templates (Manager Templates)

- Пользователь может:
  - создавать/переименовывать/удалять папки;
  - загружать шаблоны (Browse + Drag&Drop);
  - переименовывать и удалять файлы.
- Удаление файла и папки должно требовать подтверждение.
- Для шаблонов реализован сценарий **Download**:
  - по кнопке `Download` файл скачивается локально;
  - preview/open в новой вкладке не требуется.
- Загрузка `.DOCX` должна быть успешной без ошибки `Не удалось загрузить файл(ы)`.

---

## 5. Users (User Management)

- Администратор может:
  - создавать пользователей;
  - менять роль пользователя;
  - менять пароль пользователя;
  - переключать статус `active/inactive`;
  - удалять пользователя (с подтверждением).
- Ограничения безопасности:
  - нельзя удалить собственную учётную запись;
  - нельзя изменить роль собственного активного admin-аккаунта.
- Для собственного активного admin-аккаунта селект роли должен быть заблокирован (`disabled`).

---

## 6. Notifications и Logs

- Пользователь видит уведомления, может раскрывать блоки и переходить в карточку кандидата.
- Администратор видит журнал действий (Audit Logs) с фильтрами.

---

## 7. Нефункциональные ожидания

- Ошибки должны показываться понятным текстом на русском языке.
- Интерфейс должен работать в Docker-окружении проекта.
- Критические действия (удаление/смена роли/деактивация) не должны приводить к потере админ-контроля.

---

*Версия требований: 2026-04-28.*
